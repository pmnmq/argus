# ADR-001 · 用 Rust 实现 Argus

- **状态**：Accepted
- **日期**：2026-08-19
- **决策者**：架构组
- **相关**：`19-rust-project-structure.md`、`17-reliability.md`

---

## Context

Argus 是一个位于所有 AI 流量关键路径上的网关。它的核心特征：

1. **大量长连接**：SSE 流可持续 10+ 分钟，目标 10,000–50,000 并发。
2. **延迟敏感**：额外开销要控制在毫秒级，且 **p99 必须稳定**（不能有周期性尖峰）。
3. **内存敏感**：目标运行在 4C8G 甚至更小的机器上。
4. **字节处理密集**：核心工作是转发与解析字节流，需要精确控制拷贝与分配。
5. **长期运行**：进程要连续运行数月，不能有内存泄漏或性能退化。

候选语言：Rust、Go、Java/JVM、C++、Node.js。

---

## Decision

**用 Rust（edition 2024，MSRV 1.90）+ Tokio + Hyper。**

---

## Options Considered

### A. Rust ✅（选定）

**优点**
- **无 GC**：p99 延迟不受 GC 暂停影响。这对 10k 并发 SSE 是决定性的——GC 语言在这个规模下的 p99 尖峰很难消除。
- **零成本抽象与精确的内存控制**：`Bytes` 的引用计数让"一份字节两条路径"成为字面意义上的零拷贝（`10-streaming.md` §5.1）。这是整个 Tee 架构的物理基础。
- **内存占用低**：无运行时开销、无对象头、无 GC 堆预留。每流 ~54 KB 的估算（`17-reliability.md` §4.1）在 GC 语言里很难达到。
- **所有权模型天然表达取消传播**：客户端断开 → future drop → 上游连接 drop → 上游取消。这条链在 Rust 里是自动的，在其他语言里要手写（且容易漏）。
- **`Send`/`Sync` 在编译期防止并发 bug**：跨 task 共享的数据必须显式 `Arc`，误用直接编译失败。
- **生态成熟**：Hyper 是最成熟的 Rust HTTP 实现之一；rustls 让静态构建可行；Tokio 是事实标准。
- **单静态二进制**：musl + rustls → 无任何运行时依赖，直接满足部署目标。

**缺点**
- 开发速度慢于 Go/Java，尤其在异步 + 生命周期交织时（`10-streaming.md` §7.1 的借用式反序列化就是一例）。
- `Pin`/`Poll` 的手写实现（`TeeBody`）有一定门槛。
- 人才池小于 Go/Java。
- 编译时间需要主动管理（`14` §8）。

**风险**：`panic = "abort"` 会杀死整个进程。已通过 `ADR` 与 `01-architecture.md` §9 强制为 `unwind` 并配套三层隔离。

---

### B. Go ❌

**优点**
- 开发速度快，并发模型（goroutine）直观。
- `net/http` 与 SSE 处理简单。
- 单二进制、交叉编译方便。
- 人才池大。

**缺点（决定性的）**
- **GC 暂停影响 p99**。Go 的 GC 已经很好（sub-ms STW），但在 10k 活跃连接、每秒数十万次小对象分配的场景下，GC 的**辅助标记（mark assist）**会随机地拖慢某些 goroutine，表现为不可预测的延迟尖峰。这与"稳定延迟"的目标直接冲突。
- **难以做到零拷贝**。Go 的 `[]byte` 没有引用计数语义，"一份字节两条路径"需要靠约定（谁都不能改）而非类型系统保证。且 `io.Reader` 的接口设计倾向于拷贝到调用方的缓冲。
- **每 goroutine 至少 8 KB 栈**（会增长）。10k 连接 × 2–3 个 goroutine = 数百 MB 仅栈内存。
- **取消传播要手写 context 传递**，容易漏（漏了就是连接泄漏）。
- 每个 token 的解析会产生大量小对象 → GC 压力 → 见第一条。

**评价**：Go 是很合理的选择，如果目标是"1000 并发、开发速度优先"。但在 10k–50k 并发 + 低内存 + 稳定 p99 的组合下，Rust 的优势是结构性的。

---

### C. Java / JVM（Netty / Vert.x）❌

**优点**
- Netty 是工业级的网络框架，零拷贝（`ByteBuf` 引用计数）做得很好——实际上 Rust 的 `Bytes` 与 Netty 的 `ByteBuf` 思路相同。
- 生态极其成熟。
- 虚拟线程（Loom）改善了并发模型。

**缺点（决定性的）**
- **内存基线太高**。JVM 本身 + 堆预留，即使空转也要数百 MB。4C8G 的目标下，JVM 会吃掉可观的比例。这与"NAS / 家用服务器"的部署场景直接冲突。
- **GC 调优是持续的运维负担**。ZGC/Shenandoah 能把暂停压到亚毫秒，但需要额外的堆开销（通常 2–3× 活跃数据）。
- **启动慢**（数秒到数十秒），影响滚动更新与自动扩缩。
- 不是单二进制（需要 JRE，或用 GraalVM native-image 但那会失去部分生态）。
- `ByteBuf` 的手动引用计数容易泄漏（Netty 的经典问题），而 Rust 的所有权是编译期保证的。

---

### D. C++ ❌

**优点**
- 性能与内存控制的上限最高。
- 无 GC。

**缺点（决定性的）**
- **内存安全**。这是一个处理不可信输入（来自客户端与 provider 的任意字节）的网络服务。用 C++ 写解析器意味着持续的 CVE 风险。Rust 的 `#![forbid(unsafe_code)]` 从根本上消除了这一类漏洞。
- 异步生态碎片化（asio / coroutines / 各家框架），没有 Tokio 这样的事实标准。
- 构建与依赖管理（CMake/vcpkg/conan）远不如 Cargo。
- 开发与审查成本高。

**评价**：Rust 提供了 C++ 90% 的性能控制力，同时消除了它最大的风险。这个交换在 2026 年没有理由不做。

---

### E. Node.js / TypeScript ❌

**优点**
- 开发最快，AI 生态最活跃（官方 SDK 最完整）。
- SSE 处理天然。

**缺点（决定性的）**
- 单线程事件循环 + GC，无法充分利用多核（要靠 cluster，进程间无法共享连接池与缓存）。
- 内存占用高，`Buffer` 的拷贝控制困难。
- 解析密集型工作的性能与 Rust 差 10–50×。
- 长期运行的内存稳定性需要额外关注。

## Consequences

### 正面

- Tee 架构的"零拷贝"是字面意义的，不是近似（`Bytes::clone` = 一次原子加）。
- 取消传播、资源清理由 drop 语义自动保证。
- 内存与延迟可以精确核算（`17-reliability.md` §4），而不是"看 GC 心情"。
- 单静态二进制，部署形态覆盖从 NAS 到 K8s。
- `argus-protocol` 可以在编译期禁止 IO 依赖（`14` §7.2），这在动态语言里不可能。

### 负面与缓解

| 负面 | 缓解 |
|------|------|
| 开发速度慢 | 严格控制 MVP 范围（`22-mvp-roadmap.md` §4.2）；`argus-protocol` 的纯函数设计让最复杂的部分最容易测试与迭代 |
| `Pin`/`Body` 手写实现的门槛 | 只有 `TeeBody` 与 `GatedBody` 两处，其余用 Axum/Tower 的高层 API |
| 生命周期与借用式解析的复杂度 | `10-streaming.md` §7.1 明确了"借用到 Accumulator 就立刻拷贝"的边界，不让借用跨 await |
| 编译时间 | `codegen-units=4`、依赖隔离、mold 链接器（`14` §8） |
| panic = abort 的陷阱 | workspace profile 强制 unwind + CI 检查 + 三层隔离（`01` §9） |
| 人才池 | 代码风格保守（禁 unsafe、禁 unwrap、少用高级 trait 技巧） |

### 需要主动管理的

1. **不要过度使用类型系统**。这是 Rust 项目的常见失败模式（泛型嵌套、trait 体操）。规则：能用 enum dispatch 就不用 `Box<dyn>`，能用具体类型就不用泛型。
2. **异步的传染性**。`argus-protocol` 完全同步是刻意的决定，避免 async 传染到纯计算层。
3. **依赖审计**。用 `cargo-deny` 检查许可证与已知漏洞；依赖数量要克制。

---

## Notes

**关于"Rust 性能好"这个说法**：本文档刻意避免使用它作为论据。选择 Rust 的真实理由是三条**结构性**的：

1. 无 GC → p99 可预测（这是延迟目标的前提）
2. 引用计数的 `Bytes` + 所有权 → 零拷贝 tee 与自动取消传播（这是架构的前提）
3. 编译期的依赖与并发约束 → 架构不变式可强制（这是长期可维护性的前提）

如果这三条都不需要，Go 会是更快的选择。
